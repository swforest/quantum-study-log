## 왜 transpilation이 필요한가

알고리즘은 H, CX, 임의 회전 같은 추상 gate와 논리 qubit을 사용합니다. 실제 장치는 특정 native instruction, 제한된 qubit 연결, 서로 다른 오류율·지속시간을 가집니다. transpiler는 회로를 backend의 `Target` 제약에 맞게 변환합니다.

대표 단계:

1. initialization: custom instruction을 알려진 표현으로 펼침
2. layout: logical qubit을 physical qubit에 배치
3. routing: 직접 연결되지 않은 상호작용을 이동·분해
4. translation: target basis instruction으로 변환
5. optimization: 동등한 회로 안에서 비용 개선
6. scheduling: 필요할 때 시간 정보를 배치

각 단계 이름과 세부 구현은 버전에 따라 달라질 수 있지만 역할 구분은 유지됩니다.

## 작은 target으로 실험

```python
from qiskit import QuantumCircuit
from qiskit.transpiler import generate_preset_pass_manager
from qiskit.providers.fake_provider import GenericBackendV2

backend = GenericBackendV2(
    num_qubits=3,
    coupling_map=[[0, 1], [1, 2]],
)

logical = QuantumCircuit(3)
logical.h(0)
logical.cx(0, 2)

pm = generate_preset_pass_manager(
    backend=backend,
    optimization_level=1,
    seed_transpiler=7,
)
isa = pm.run(logical)

print(logical.draw("text"))
print(isa.draw("text"))
print(isa.layout)
```

설치 버전에 따라 `GenericBackendV2` 생성자 옵션이 달라질 수 있으므로 signature를 확인합니다.

## ISA라는 말

ISA circuit은 선택한 backend의 target이 지원하는 instruction과 physical qubit에 맞는 회로입니다. `transpile을 한 번 했다`는 사실만으로 어떤 backend에도 실행 가능한 것은 아닙니다. backend가 달라지면 target이 달라지므로 다시 변환·검증해야 합니다.

## 동등성 검증

measurement 없는 작은 unitary 회로는 `Operator.equiv`로 확인할 수 있지만 physical layout과 ancilla가 포함되면 단순 행렬 차원이 달라질 수 있습니다. 가능한 검증 방법:

- 작은 회로: Operator 또는 Statevector 비교
- 대표 입력 상태 테스트
- measurement 분포 비교
- `final_index_layout`을 반영한 bit mapping 확인
- Qiskit transpiler verification pass·테스트 활용

회로 그림이 달라졌다는 이유로 의미가 달라졌다고 판단하지 않습니다.

## 과제

1. 직접 연결되지 않은 CX를 만들고 routing 전후 gate 수를 비교합니다.
2. same logical circuit을 line·fully connected coupling map에 각각 transpile합니다.
3. `count_ops`, `depth`, `size`, layout을 표로 기록합니다.
4. 출력 instruction이 backend target에 포함되는지 검사합니다.

## 2. 핵심 유도와 손계산

### 수학·논리 전개

transpilation은 논리 유니터리를 target basis로 합성하고 layout을 정한 뒤 coupling graph를 만족하도록 routing permutation을 삽입합니다. 이상적으로는 최종 논리 동작이 원본과 같지만 물리 선과 gate sequence는 달라집니다.

이 문장을 그대로 암기하지 말고 다음 순서로 다시 전개합니다.

1. 출발하는 상태, 데이터, 변수 또는 가정을 먼저 씁니다.

2. 적용되는 게이트, 행렬, 치환, API 변환을 한 단계씩 분리합니다.

3. 단계마다 보존되어야 하는 정규화, 차원, type, shape, mapping을 확인합니다.

4. 마지막 식이나 객체가 오늘 중심 질문에 어떤 답을 주는지 한 문장으로 연결합니다.

5. 부호, 순서, 인덱스 가운데 하나를 바꾸었을 때 결과가 어떻게 달라지는지 반례를 만듭니다.

### 손으로 따라가는 예제

선형 연결 0-1-2에서 논리 q0와 q2 사이 CX가 필요하면 직접 간선이 없어 SWAP 또는 등가 routing이 추가됩니다. 초기 layout을 바꾸면 추가 2큐비트 gate 수가 달라질 수 있습니다.

#### 예제 재현 절차

- 첫 번째 시도에서는 코드를 실행하지 않습니다.
- 입력과 가능한 출력 후보를 종이에 적습니다.
- 중간 상태 또는 중간 값을 최소 두 단계 기록합니다.
- 마지막에만 기존 본문의 코드와 비교합니다.
- 값이 다르면 정답을 고치기 전에 convention과 순서를 먼저 확인합니다.

### 출력 해석 기준

원본과 ISA 회로의 size, depth, 2큐비트 gate 수를 표로 비교하고 layout을 별도 열에 기록합니다. 회로 그림의 wire 번호만으로 논리 변수의 최종 위치를 추측하지 않습니다.

#### 출력에서 반드시 구별할 것

- 정확한 이론값인지 유한 샷 추정치인지 표시합니다.
- 배열의 각 축과 문자열의 각 비트가 무엇을 뜻하는지 표시합니다.
- 회로 구조가 맞다는 증거와 물리적 결과가 맞다는 증거를 분리합니다.
- 수치가 우연히 맞아도 잘못된 mapping이 가려졌을 가능성을 확인합니다.

## 4. 예측 중심 통합 실험

### 실험 질문

연결성이 제한된 GenericBackendV2 또는 선택 backend에 같은 회로를 여러 초기 layout으로 transpile하고 연산 수, depth, layout을 비교합니다.

### 실행 전에 적을 내용

1. 입력 상태 또는 입력 데이터의 크기와 순서를 적습니다.

2. 회로나 수식이 적용되는 순서를 한 단계씩 번호로 씁니다.

3. 정확히 예측할 수 있는 출력과 유한 샷 때문에 흔들릴 출력을 구분합니다.

4. 성공을 판정할 수치 또는 구조적 조건을 하나 정합니다.

5. 실패했을 때 가장 먼저 출력할 type, shape, mapping, version을 적습니다.

### 예상 결과

지원되지 않는 게이트는 basis instruction으로 분해되고 멀리 떨어진 상호작용에는 routing 연산이 추가되며 논리-물리 매핑이 달라질 수 있습니다.

| 배열 또는 결과 shape |  |  |  |
| 가능한 basis·bitstring |  |  |  |
| 핵심 수치 |  |  |  |
| 회로 size·depth |  |  |  |
| mapping·register |  |  |  |

### 실행 후 비교 순서

1. 코드가 실행됐다는 사실과 결과가 맞다는 판단을 분리합니다.

2. 먼저 type과 shape가 예측과 같은지 확인합니다.

3. 다음으로 basis 순서, parameter 순서, register 이름을 확인합니다.

4. 정확한 이론값과 샷 기반 추정치를 같은 허용 오차로 비교하지 않습니다.

- 구형 예제의 import와 현재 API를 이름만 바꾸지 말고 목적별로 매핑합니다.

### 2단계: 입력

- qubit 수, classical bit 수, parameter 수를 적습니다.
- 배열 shape와 axis 의미를 적습니다.
- bitstring과 Pauli 문자열의 변수 순서를 적습니다.

### 3단계: 변환

- 회로 instruction 순서와 compose 순서를 확인합니다.
- transpilation이 있다면 원본과 ISA 회로를 분리합니다.
- layout, register mapping, parameter binding을 출력합니다.

### 4단계: 출력

- result 객체를 추측하지 않고 type, 첫 PUB, data, key 순서로 내려갑니다.
- 정확값, 기대값, 샷 counts 가운데 지금 얻은 결과의 종류를 적습니다.
- 값이 아니라 shape부터 예측과 비교합니다.

### 5단계: 의미

- 코드가 성공했다는 사실만으로 물리적·수학적 정답이라고 결론 내리지 않습니다.
- 독립적인 손계산 또는 brute-force 기준선과 비교합니다.
- 남은 차이를 모델 오류, 구현 오류, 통계 변동으로 분류합니다.
