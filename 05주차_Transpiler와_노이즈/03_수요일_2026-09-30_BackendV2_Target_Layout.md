# 5주차 수요일 - BackendV2, Target, Layout

## 목표

- BackendV2가 제공하는 실행 제약을 `target` 중심으로 읽습니다.
- logical qubit과 physical qubit을 구분합니다.
- initial·final layout과 측정 결과 mapping을 설명합니다.
- 구형 `configuration()` 중심 예제를 현대화합니다.

## BackendV2

BackendV2는 backend 이름, qubit 수, Target, 실행 interface 등을 제공합니다. BackendV1의 중첩된 configuration·properties를 그대로 가정하지 않습니다.

```python
print(backend.name)
print(backend.num_qubits)
print(backend.operation_names)
print(backend.target)
```

## Target

Target은 instruction별 지원 qubit tuple과 properties를 표현합니다. 다음 질문에 답하는 중심 객체입니다.

- 이 gate를 어느 physical qubit에서 지원하는가?
- 이 2-qubit interaction은 어느 방향으로 가능한가?
- instruction duration·error 정보가 있는가?
- measurement와 reset이 지원되는가?

정보가 `None`일 수 있으므로 모든 fake·simulator backend에 실제 calibration data가 있다고 가정하지 않습니다.

## layout

논리 회로 q0가 실제 physical qubit 0에 갈 필요는 없습니다. layout은 논리→물리 mapping을 표현합니다. routing 과정에서 qubit 상태가 이동하면 final mapping도 중요합니다.

```python
print(isa.layout)

if isa.layout is not None:
    print(isa.layout.initial_layout)
    print(isa.layout.final_layout)
```

API 세부 속성은 설치 버전에서 확인합니다. 중요한 것은 measurement 결과를 원래 논리 bit 의미로 되돌릴 때 layout과 classical mapping을 함께 고려한다는 점입니다.

## coupling direction

연결 graph에 edge가 있어도 gate direction이 제한될 수 있습니다. transpiler는 방향을 뒤집기 위해 추가 basis changes를 삽입할 수 있습니다. `연결되어 있다`와 `원하는 native gate를 원하는 방향으로 바로 실행할 수 있다`를 구분합니다.

## 과제

1. backend target의 operation 이름과 qargs를 표로 출력합니다.
2. 3논리 qubit 회로를 5physical qubit backend에 transpile하고 initial layout을 기록합니다.
3. explicit `initial_layout` 두 개를 비교합니다.
4. 가장 적은 2-qubit gate를 만드는 layout과 가장 얕은 layout을 비교합니다.

## 구형 코드 현대화

구형:

```python
backend.configuration().basis_gates
backend.configuration().coupling_map
backend.properties()
```

현재는 우선 `backend.target`, `backend.operation_names`, `backend.num_qubits`와 target instruction properties를 사용합니다.

## 2. 핵심 유도와 손계산

### 수학·논리 전개

Target은 instruction 이름만이 아니라 허용 qargs별 properties를 갖는 관계입니다. operation_names에 cx가 있어도 모든 ordered pair에서 cx를 실행할 수 있다는 뜻은 아니며 coupling 방향은 ordered qargs로 읽어야 합니다.

이 문장을 그대로 암기하지 말고 다음 순서로 다시 전개합니다.

1. 출발하는 상태, 데이터, 변수 또는 가정을 먼저 씁니다.

2. 적용되는 게이트, 행렬, 치환, API 변환을 한 단계씩 분리합니다.

3. 단계마다 보존되어야 하는 정규화, 차원, type, shape, mapping을 확인합니다.

4. 마지막 식이나 객체가 오늘 중심 질문에 어떤 답을 주는지 한 문장으로 연결합니다.

5. 부호, 순서, 인덱스 가운데 하나를 바꾸었을 때 결과가 어떻게 달라지는지 반례를 만듭니다.

### 손으로 따라가는 예제

3큐비트 target에서 cx가 (0,1)과 (1,2)에만 있으면 논리 (0,2) 상호작용은 직접 실행할 수 없습니다. layout과 routing 뒤 어느 physical pair의 cx로 분해됐는지 확인합니다.

#### 예제 재현 절차

- 첫 번째 시도에서는 코드를 실행하지 않습니다.
- 입력과 가능한 출력 후보를 종이에 적습니다.
- 중간 상태 또는 중간 값을 최소 두 단계 기록합니다.
- 마지막에만 기존 본문의 코드와 비교합니다.
- 값이 다르면 정답을 고치기 전에 convention과 순서를 먼저 확인합니다.

### 출력 해석 기준

target의 operation names, qargs, error, duration을 계층적으로 출력합니다. TranspileLayout의 initial과 final mapping을 원래 논리 변수 표에 다시 붙여 observable과 측정 decoder가 같은 순서를 쓰게 합니다.

#### 출력에서 반드시 구별할 것

- 정확한 이론값인지 유한 샷 추정치인지 표시합니다.
- 배열의 각 축과 문자열의 각 비트가 무엇을 뜻하는지 표시합니다.
- 회로 구조가 맞다는 증거와 물리적 결과가 맞다는 증거를 분리합니다.
- 수치가 우연히 맞아도 잘못된 mapping이 가려졌을 가능성을 확인합니다.

### 실행 전에 적을 내용

## 7. 실패 진단 절차

오늘 가장 가능성 높은 실패는 다음과 같습니다. 구형 configuration와 properties 접근을 그대로 사용하거나 operation_names만 보고 모든 큐비트에 게이트가 가능하다고 가정하면 오류가 납니다.

### 1단계: 환경

- Python, Qiskit, 선택 패키지 버전을 출력합니다.
- 노트북 kernel과 패키지를 설치한 interpreter가 같은지 확인합니다.
- 구형 예제의 import와 현재 API를 이름만 바꾸지 말고 목적별로 매핑합니다.

### 2단계: 입력

- qubit 수, classical bit 수, parameter 수를 적습니다.
- 배열 shape와 axis 의미를 적습니다.
- bitstring과 Pauli 문자열의 변수 순서를 적습니다.

### 3단계: 변환

- 회로 instruction 순서와 compose 순서를 확인합니다.
- transpilation이 있다면 원본과 ISA 회로를 분리합니다.
- layout, register mapping, parameter binding을 출력합니다.

### 4단계: 출력

- result 객체를 추측하지 않고 type, 첫 PUB, data, key 순서로 내려갑니다.
- 정확값, 기대값, 샷 counts 가운데 지금 얻은 결과의 종류를 적습니다.
- 값이 아니라 shape부터 예측과 비교합니다.

### 5단계: 의미

- 코드가 성공했다는 사실만으로 물리적·수학적 정답이라고 결론 내리지 않습니다.
- 독립적인 손계산 또는 brute-force 기준선과 비교합니다.
- 남은 차이를 모델 오류, 구현 오류, 통계 변동으로 분류합니다.
