# 5주차 화요일 - 최적화 수준과 PassManager

## 목표

- preset optimization level 0~3의 의도를 비교합니다.
- `seed_transpiler`에 따른 stochastic 결과 변화를 관찰합니다.
- depth, 2-qubit gate count, estimated error 등 여러 비용 기준을 구분합니다.
- PassManager 결과를 맹목적으로 신뢰하지 않고 측정합니다.

## optimization level

일반적인 직관:

- level 0: 최소 변환, 빠른 baseline
- level 1: 가벼운 최적화
- level 2: 더 많은 분석과 최적화
- level 3: 가장 적극적인 최적화, compile 시간 증가 가능

숫자가 높다고 모든 지표가 항상 좋아지는 것은 아닙니다. routing의 확률적 선택, target 특성, metric의 충돌 때문에 depth는 줄고 2-qubit gate 수는 늘 수 있습니다.

## 실험 설계

```python
from qiskit.transpiler import generate_preset_pass_manager

rows = []

for level in range(4):
    for seed in [1, 2, 3, 4, 5]:
        pm = generate_preset_pass_manager(
            backend=backend,
            optimization_level=level,
            seed_transpiler=seed,
        )
        out = pm.run(logical)
        rows.append({
            "level": level,
            "seed": seed,
            "depth": out.depth(),
            "size": out.size(),
            "two_qubit": sum(
                count for name, count in out.count_ops().items()
                if name in {"cx", "cz", "ecr", "swap"}
            ),
        })
```

target의 native 2-qubit gate가 무엇인지 확인하지 않고 CX만 세면 잘못된 metric이 됩니다.

## PassManager와 staged pipeline

Pass는 회로의 분석 또는 변환 작업입니다.

- AnalysisPass: property set을 계산
- TransformationPass: DAG circuit을 변경

preset pass manager는 stage로 구성될 수 있습니다. 커스텀 pass를 넣기 전에 어떤 stage의 invariant를 가정하는지 이해해야 합니다.

## metric 선택

실제 실행 품질에 중요한 대표 항목:

- 2-qubit gate 수와 error
- circuit depth
- duration
- readout assignment
- coherence time 대비 실행 시간
- dynamical decoupling·twirling 등 runtime option

단순 gate 총수는 좋은 출발점이지만 충분한 목표 함수가 아닙니다.

## 과제

1. Grover·GHZ 회로를 level×seed grid로 transpile합니다.
2. 최선의 회로를 depth 기준과 2-qubit gate 기준으로 따로 선택합니다.
3. 두 선택이 다르면 어느 것을 선호할지 근거를 씁니다.
4. 같은 seed로 재실행했을 때 재현성을 확인합니다.

## 완료 기준

- [ ] level별 결과 표를 만들었다.
- [ ] seed의 역할을 설명했다.
- [ ] metric 두 개 이상이 충돌하는 예를 찾았다.
- [ ] 최적화를 의미 보존과 별도로 검증했다.

## 2. 핵심 유도와 손계산

### 수학·논리 전개

pass manager는 분석 결과를 property set에 축적하고 transformation pass가 DAG를 바꾸는 순서 있는 함수 합성입니다. 앞 단계의 layout과 routing 선택이 뒤의 translation과 optimization이 볼 회로 구조를 결정합니다.

이 문장을 그대로 암기하지 말고 다음 순서로 다시 전개합니다.

1. 출발하는 상태, 데이터, 변수 또는 가정을 먼저 씁니다.

2. 적용되는 게이트, 행렬, 치환, API 변환을 한 단계씩 분리합니다.

3. 단계마다 보존되어야 하는 정규화, 차원, type, shape, mapping을 확인합니다.

4. 마지막 식이나 객체가 오늘 중심 질문에 어떤 답을 주는지 한 문장으로 연결합니다.

5. 부호, 순서, 인덱스 가운데 하나를 바꾸었을 때 결과가 어떻게 달라지는지 반례를 만듭니다.

### 손으로 따라가는 예제

H-H, X-X, RZ(a)-RZ(b)처럼 취소와 결합이 가능한 회로를 level별로 비교합니다. 단일 큐비트 gate 수는 줄어도 제한된 coupling에서 routing 결과가 달라지면 전체 depth는 다른 방향으로 움직일 수 있습니다.

#### 예제 재현 절차

- 첫 번째 시도에서는 코드를 실행하지 않습니다.
- 입력과 가능한 출력 후보를 종이에 적습니다.
- 중간 상태 또는 중간 값을 최소 두 단계 기록합니다.
- 마지막에만 기존 본문의 코드와 비교합니다.
- 값이 다르면 정답을 고치기 전에 convention과 순서를 먼저 확인합니다.

### 출력 해석 기준

같은 원본, backend, seed_transpiler로 각 level을 여러 번 비교합니다. 총 gate 수 외에 2큐비트 gate 수와 depth를 함께 기록하고 개선 목표를 먼저 선언한 뒤 winner를 고릅니다.

#### 출력에서 반드시 구별할 것

- 정확한 이론값인지 유한 샷 추정치인지 표시합니다.
- 배열의 각 축과 문자열의 각 비트가 무엇을 뜻하는지 표시합니다.
- 회로 구조가 맞다는 증거와 물리적 결과가 맞다는 증거를 분리합니다.
- 수치가 우연히 맞아도 잘못된 mapping이 가려졌을 가능성을 확인합니다.
- 다음 사람이 같은 결론을 재현할 수 있도록 버전과 seed를 남깁니다.

## 4. 예측 중심 통합 실험

### 실험 질문

역게이트와 불필요한 회전이 섞인 회로를 optimization level별로 변환하고 staged pass manager의 단계별 결과를 기록합니다.

### 실행 전에 적을 내용

1. 입력 상태 또는 입력 데이터의 크기와 순서를 적습니다.

2. 회로나 수식이 적용되는 순서를 한 단계씩 번호로 씁니다.

3. 정확히 예측할 수 있는 출력과 유한 샷 때문에 흔들릴 출력을 구분합니다.

4. 성공을 판정할 수치 또는 구조적 조건을 하나 정합니다.

5. 실패했을 때 가장 먼저 출력할 type, shape, mapping, version을 적습니다.

### 예상 결과

단순 취소와 회전 결합으로 size와 depth가 줄 수 있지만 routing 선택 때문에 특정 지표는 비단조적으로 변할 수 있습니다.

### 실험 기록표

| 항목 | 실행 전 예측 | 실제 결과 | 차이의 원인 |
|---|---|---|---|
| 객체 type |  |  |  |
| 배열 또는 결과 shape |  |  |  |
| 가능한 basis·bitstring |  |  |  |
| 핵심 수치 |  |  |  |
| 회로 size·depth |  |  |  |
| mapping·register |  |  |  |

### 실행 후 비교 순서

1. 코드가 실행됐다는 사실과 결과가 맞다는 판단을 분리합니다.

2. 먼저 type과 shape가 예측과 같은지 확인합니다.

3. 다음으로 basis 순서, parameter 순서, register 이름을 확인합니다.

4. 정확한 이론값과 샷 기반 추정치를 같은 허용 오차로 비교하지 않습니다.

5. 차이가 남으면 오류 메시지와 최소 재현 코드를 별도 셀에 보존합니다.

## 7. 실패 진단 절차

오늘 가장 가능성 높은 실패는 다음과 같습니다. seed를 고정하지 않고 결과 한 번만 비교하거나 전체 gate 수만 보고 오류가 큰 2큐비트 gate 증가를 놓치면 잘못된 결론을 냅니다.

### 1단계: 환경

- Python, Qiskit, 선택 패키지 버전을 출력합니다.
- 노트북 kernel과 패키지를 설치한 interpreter가 같은지 확인합니다.
- 구형 예제의 import와 현재 API를 이름만 바꾸지 말고 목적별로 매핑합니다.

### 2단계: 입력

- qubit 수, classical bit 수, parameter 수를 적습니다.
- 배열 shape와 axis 의미를 적습니다.
- bitstring과 Pauli 문자열의 변수 순서를 적습니다.

### 3단계: 변환

- 회로 instruction 순서와 compose 순서를 확인합니다.
- transpilation이 있다면 원본과 ISA 회로를 분리합니다.
- layout, register mapping, parameter binding을 출력합니다.

### 4단계: 출력

- result 객체를 추측하지 않고 type, 첫 PUB, data, key 순서로 내려갑니다.
- 정확값, 기대값, 샷 counts 가운데 지금 얻은 결과의 종류를 적습니다.
- 값이 아니라 shape부터 예측과 비교합니다.

### 5단계: 의미

- 코드가 성공했다는 사실만으로 물리적·수학적 정답이라고 결론 내리지 않습니다.
- 독립적인 손계산 또는 brute-force 기준선과 비교합니다.
- 남은 차이를 모델 오류, 구현 오류, 통계 변동으로 분류합니다.
