## observable layout

논리 observable `ZI`는 logical qubit 의미를 갖습니다. transpilation 후 logical qubit이 다른 physical qubit에 배치되면 observable도 layout에 맞춰야 합니다.

```python
isa_circuit = pm.run(ansatz)
isa_observable = observable.apply_layout(isa_circuit.layout)
```

이를 생략하면 회로 상태와 다른 physical qubit을 측정하는 잘못된 기대값을 요청할 수 있습니다.

## 제출 골격

실제 제출 승인 후에만 실행합니다.

```python
from qiskit_ibm_runtime import EstimatorV2

estimator = EstimatorV2(mode=backend)
pub = (isa_circuit, isa_observable, [parameter_values])
job = estimator.run([pub], precision=0.02)

pub_result = job.result()[0]
print(pub_result.data.evs)
print(pub_result.data.stds)
print(pub_result.metadata)
```

parameter array shape를 현재 API example과 대조합니다.

## 실행 모드

### Job mode

독립적인 한두 작업에 단순합니다. 각 job이 별도로 스케줄됩니다.

### Session mode

고전 optimizer와 quantum evaluation이 반복되는 variational workload에 유리할 수 있습니다. session에는 최대 지속시간·interactive TTL 등 운영 제약이 있으므로 현재 문서를 확인합니다.

### Batch mode

서로 독립적인 여러 job을 한 묶음으로 제출해 throughput을 높이는 용도입니다. 이전 결과에 따라 다음 parameter를 정하는 순차 optimizer와는 성격이 다릅니다.

## precision과 shots

Estimator는 target precision 중심 interface를 사용할 수 있습니다. 더 작은 precision은 일반적으로 더 많은 quantum work를 요구합니다. `precision=0.01`이 결과가 정확히 소수 둘째 자리까지 맞는다는 보장은 아닙니다.

## resilience

Estimator option의 resilience level·mitigation suboptions는 현재 Runtime version에서 확인합니다. 높은 수준이 무조건 값싸고 정확한 것은 아닙니다.

- 더 많은 circuits·shots·model overhead 가능
- bias 감소와 variance 증가 trade-off
- observable·circuit·noise regime에 따라 효과 다름

## 2. 핵심 유도와 손계산

### 수학·논리 전개

논리 회로가 layout L로 물리 큐비트에 배치되면 observable도 같은 permutation을 적용해야 동일한 논리량을 측정합니다. 실행 mode는 expectation의 수학 정의를 바꾸지 않지만 workload 스케줄링과 반복 호출 지연을 바꿉니다.

이 문장을 그대로 암기하지 말고 다음 순서로 다시 전개합니다.

1. 출발하는 상태, 데이터, 변수 또는 가정을 먼저 씁니다.

2. 적용되는 게이트, 행렬, 치환, API 변환을 한 단계씩 분리합니다.

3. 단계마다 보존되어야 하는 정규화, 차원, type, shape, mapping을 확인합니다.

4. 마지막 식이나 객체가 오늘 중심 질문에 어떤 답을 주는지 한 문장으로 연결합니다.

5. 부호, 순서, 인덱스 가운데 하나를 바꾸었을 때 결과가 어떻게 달라지는지 반례를 만듭니다.

### 손으로 따라가는 예제

논리 q0의 Z를 관측하는데 layout이 q0을 physical 3에 두었다면 observable은 physical 3의 Z로 옮겨야 합니다. apply_layout 없이 원래 위치를 읽으면 다른 큐비트 기대값을 정상적으로 계산하고도 틀린 답을 얻습니다.

#### 예제 재현 절차

## 4. 예측 중심 통합 실험

### 실험 질문

같은 매개변수 sweep workload를 독립 job, 반복 상호작용 session, 미리 묶은 batch 관점으로 설계하고 호출 수와 실패 복구 지점을 비교합니다.

### 실행 전에 적을 내용

1. 입력 상태 또는 입력 데이터의 크기와 순서를 적습니다.

2. 회로나 수식이 적용되는 순서를 한 단계씩 번호로 씁니다.

3. 정확히 예측할 수 있는 출력과 유한 샷 때문에 흔들릴 출력을 구분합니다.

4. 성공을 판정할 수치 또는 구조적 조건을 하나 정합니다.

5. 실패했을 때 가장 먼저 출력할 type, shape, mapping, version을 적습니다.

### 예상 결과

transpiled layout이 바뀌면 observable에도 apply_layout이 필요하고 실행 모드는 계산 의미보다 스케줄링과 상호작용 패턴을 바꿉니다.

|---|---|---|---|
| 객체 type |  |  |  |
| 배열 또는 결과 shape |  |  |  |
| 가능한 basis·bitstring |  |  |  |
| 핵심 수치 |  |  |  |
| 회로 size·depth |  |  |  |
| mapping·register |  |  |  |

### 실행 후 비교 순서

1. 코드가 실행됐다는 사실과 결과가 맞다는 판단을 분리합니다.

2. 먼저 type과 shape가 예측과 같은지 확인합니다.

3. 다음으로 basis 순서, parameter 순서, register 이름을 확인합니다.

4. 정확한 이론값과 샷 기반 추정치를 같은 허용 오차로 비교하지 않습니다.

5. 차이가 남으면 오류 메시지와 최소 재현 코드를 별도 셀에 보존합니다.

## 7. 실패 진단 절차

오늘 가장 가능성 높은 실패는 다음과 같습니다. 논리 observable을 물리 layout에 맞추지 않거나 precision과 shots의 관계를 고정 공식처럼 가정하면 기대값이 잘못되거나 비용 예측이 틀립니다.

### 1단계: 환경

- Python, Qiskit, 선택 패키지 버전을 출력합니다.
- 노트북 kernel과 패키지를 설치한 interpreter가 같은지 확인합니다.
- 구형 예제의 import와 현재 API를 이름만 바꾸지 말고 목적별로 매핑합니다.

### 2단계: 입력

- qubit 수, classical bit 수, parameter 수를 적습니다.
- 배열 shape와 axis 의미를 적습니다.
- bitstring과 Pauli 문자열의 변수 순서를 적습니다.

### 3단계: 변환

- 회로 instruction 순서와 compose 순서를 확인합니다.
- transpilation이 있다면 원본과 ISA 회로를 분리합니다.
- layout, register mapping, parameter binding을 출력합니다.

### 4단계: 출력

- result 객체를 추측하지 않고 type, 첫 PUB, data, key 순서로 내려갑니다.
- 정확값, 기대값, 샷 counts 가운데 지금 얻은 결과의 종류를 적습니다.
- 값이 아니라 shape부터 예측과 비교합니다.

### 5단계: 의미

- 코드가 성공했다는 사실만으로 물리적·수학적 정답이라고 결론 내리지 않습니다.
- 독립적인 손계산 또는 brute-force 기준선과 비교합니다.
- 남은 차이를 모델 오류, 구현 오류, 통계 변동으로 분류합니다.
